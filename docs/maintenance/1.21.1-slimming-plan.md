# MSK 1.21.1 Fork 专项瘦身审计与实施计划

## 1. 文档定位

本文档是 `DemSum/MaidsoulKitchen` 的 `brewery/1.21.1-slim` 分支进行源码瘦身、架构收敛和后续上游同步时的控制文档。

目标不是为了减少行数而删除功能，而是重新建立以下能力：

- 能明确说明每个主要包、任务、Mixin 和兼容层为何存在。
- 正式 JAR 只携带当前产品确实使用的运行时代码。
- 构建期分析工具、实验性 API、废弃原型和正式运行时代码互相隔离。
- 上游同步、功能移植、兼容修复和架构重构分别提交、分别验证。
- 每一轮删除都具备证据、测试门槛和可独立回退的提交。

本文档不会替代 [`docs/upstream-sync/0.1.4.md`](../upstream-sync/0.1.4.md) 中的上游来源记录、校验值和 credits。

## 3. 不可突破的边界

### 3.1 仓库与发布边界

- 未经明确要求，不推送 private patch backup 的 `main`。
- `Maidsoul-Brewery-Public/main` 只有在它自身发生确认过的改动时才推送。
- 专项瘦身期间不移动已有 tag，不因清理代码单独更新版本号。
- 不修改 CurseForge 测试实例，不替换实例内 JAR；测试 JAR 由维护者手动覆盖。
- 正式 fork 稳定前，不提前删除 Public patch 中的两个临时坐标 Mixin。

### 3.2 代码与授权边界

- 保留 MaidsoulKitchen 及实际复用来源的清晰 credits。
- SimplePathfinder 继续只作为设计参考；若未来复制源码，必须先确认许可证并更新 README。
- 不把“未发现仓库内调用”直接等同于“可以删除公开 API”。公开类型必须经过兼容策略决定。
- 不把 Mixin、事件订阅类、TLM 扩展、JEI/REI/EMI 插件等依靠框架发现的入口误判为普通孤立类。

### 3.3 首轮保护区

S0 和 S1 阶段不得顺手重写以下功能：

- `CookTargetState` 和 `WORK_POS` 双坐标状态。
- `ReachableCookDeviceSearch` 的一次性 BFS/可达侧面搜索。
- 通用 `MaidCookMoveTask` / `MaidCookMakeTask` 的设备坐标与落脚坐标分离。
- DrinkBeer 输入、杯子/桶回收、mark-dirty 修复。
- Kaleidoscope Cookery 蒸笼适配和过滤数据。
- TLM 1.5.3 女仆背包兼容层。
- 当前已注册的熔炉、厨锅、砧板、煎锅、烧烤、妖怪归乡等任务。

### 5.4 D 级：兼容检查器架构重构

`modclazzchecker` 不能整目录直接删除，因为它当前承担：

1. 模组、版本、配置和依赖任务的加载判断。
2. 可选模组缺失时的兼容 Mixin 过滤。
3. 外部类、方法、字段的运行时兼容验证。
4. 客户端登录后的兼容错误报告。
5. `runData` 时生成兼容清单。

已确认的问题：

- `CommonRegistry` 的 FML setup 和 `MaidPlugin` 构造器都会调用 `mccInit()`，初始化不是幂等的。
- 客户端重复初始化会重复注册 `ReportErrorEvent`。
- `clazzLoad()` 对未知 UID 和未初始化结果默认返回 `true`，属于 fail-open。
- 存在两套 `TaskInfo`、两套 `Mods`、两套 `ModUtil`。
- `TaskLoadError` 位于通用包中，却直接导入客户端 `Minecraft` 和 `LanguageManager`。
- 构建期 ASM 分析、运行时验证、Mixin 早期加载和客户端报告混在同一个正式 source set。

目标架构应拆成：

- 单一 `CompatibilityRegistry`：任务 UID、模组版本、配置和任务依赖的唯一来源。
- 轻量运行时检查：只保留实际任务所需的加载判断。
- 轻量 Mixin gate：在 Mixin plugin 阶段读取同一份静态兼容信息。
- 客户端错误报告：放入明确的 client-only 包和初始化入口。
- 构建工具：ASM 分析和清单生成移入独立 source set，不打入正式 JAR。

## 8. 每次删除前的证据规则

任何源码删除至少要完成以下检查：

1. 用 `rg` 检查 Java、资源、Gradle、文档和测试中的直接引用。
2. 检查是否由注解、服务文件、Mixin JSON、TLM 扩展或模组事件总线发现。
3. 检查构建 JAR 中是否存在对应 class，以及是否存在其他 class 的字节码引用。
4. 若类型为 `public`，记录外部 API 兼容决定。
5. 若涉及任务 UID、配置键或 `TaskDataKey`，检查旧存档和旧配置。
6. 删除后单独提交，不与新功能、上游同步或格式化混合。
7. 通过该阶段门槛后，才开始下一组删除。

这些决定没有完成前，S2 不得开始删除相应代码。

## 10. 上游同步规则

- 上游新版本先落到独立 vendor/sync 分支，不直接覆盖 `brewery/1.21.1-slim`。
- 分别审查任务功能、兼容 API、Mixin、配置/数据结构和构建系统差异。
- 只迁移仍在当前产品范围内的功能，不因“上游存在”自动引入实验包和历史原型。
- 每次同步更新 `docs/upstream-sync/`，记录来源 commit、校验值和本 fork 保留/拒绝的改动。
- 上游同步提交与本地瘦身提交不得混合，以便独立回退和重新评估。
